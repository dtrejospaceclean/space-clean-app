# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`sp_cln_app` is a Flutter **mobile** app (Android and iOS only; Dart SDK `^3.13.4`) for a REST backend documented in `docs/frontend-api.md` (endpoints, envelope, permission model) and `docs/api-message-keys.md` (every translation key the API can return). `docs/` is git-ignored, so read those files locally before building a feature against an endpoint. The backend source (NestJS + Prisma) is at `D:\DevProjects\sp_cln_be`. Its DTOs (`src/**/dto/*.ts`) are the exact request contract (unknown fields are rejected), and they cover details the docs leave out, such as which fields `PATCH` accepts.

Stack: Riverpod 3 (no codegen), Dio, go_router, flutter_secure_storage, shared_preferences, flutter_svg, shimmer, firebase_messaging + flutter_local_notifications, gen-l10n (English + Spanish).

Product and design context: `PRODUCT.md` (users, roles, principles, accessibility) and `DESIGN.md` (visual system). Read them before UI work.

flutter test --update-goldens tool/brand         # re-render splash, launcher and notification icon PNGs from the SVGs in assets/brand

On a Windows dev machine, building with plugins requires Developer Mode (symlink support).

The app is mobile only. Don't add web or desktop code paths (`kIsWeb`, desktop-only plugins). The backend also doesn't send CORS headers, so a web build couldn't reach it.

## Architecture: Clean Architecture, feature-first

```
lib/core/                 cross-cutting: error/ (Failure), usecase/, network/, storage/, di/, router/, l10n/, theme/, widgets/
lib/features/<feature>/
  domain/                 entities/, repositories/ (abstract interfaces), usecases/  — pure Dart
  data/                   models/ (JSON → entity), datasources/, repositories/ (*_impl)
  presentation/           controllers/ (Riverpod notifiers), screens/
  di/                     <feature>_providers.dart — composition root
```

**Dependency rule, which must hold:**
- `domain/` imports only other domain code, `core/error`, `core/usecase` and `core/domain` (shared value types such as `Priority`, and `money.dart`: `toCents`, `centsToDecimal`, `lineTotalCents`): no Flutter, Dio, Riverpod or `data/`.
- `presentation/` never imports `data/` or `core/network`. Controllers call use cases, and screens catch `Failure`.
- Only `di/` files know the concrete `*Impl` classes.

**Adding a feature** follows the auth layout:
1. Entity plus an abstract repository in `domain/`, with one use case class per action (`UseCase<T, Params>`, called via `call`).
2. A remote data source that calls `ApiClient` and throws `ApiException`. A model that maps JSON to the entity.
3. A `*RepositoryImpl` that wraps every call so each `ApiException` becomes a `Failure` via `toFailure()` (see `_guard` in `AuthRepositoryImpl`).
4. Providers in `di/`, then controllers and screens.

**Errors:** every error surfaced to the UI is a domain `Failure` (`core/error/failures.dart`): `NetworkFailure`, `UnauthorizedFailure` (401), `ValidationFailure` (field errors keyed by request-body path) or `ServerFailure`. `messageKey` is the API's translation key, never display text. `lib/core/l10n/failure_messages.dart` turns keys into localized strings (`failureMessage`, `fieldError`). Add a case there whenever a feature starts surfacing a new key.

**API layer (`core/network/`)**
- `ApiClient` unwraps the `{ success, message, data, errors, statusCode }` envelope.
- `AuthInterceptor` attaches the bearer token. On 401 with `auth.invalid_access_token`/`auth.missing_token`, it refreshes once through a separate interceptor-less Dio, with concurrent 401s sharing one refresh, and then replays the request. Any refused refresh (a 4xx other than 408/429), or a replay still refused with fresh tokens, calls `TokenStorage.expireSession()`, which emits on `sessionExpired`; `AuthController` listens through the `WatchSessionExpired` use case and the router goes to sign-in. Offline, a timeout, 408/429 or 5xx during refresh keep the session, and the request fails with that error instead of the 401 (which would read "session expired"). `test/features/auth/presentation/session_expiry_test.dart` runs the real chain with only the HTTP adapter faked.
- Public calls pass `authenticated: false`.
- The backend rejects unknown body fields (`validation.whitelist_validation`), so send only the fields an endpoint defines.

**Session and routing**
- `authControllerProvider` (`AsyncNotifier<AuthState>`, sealed `Authenticated(user)` / `Unauthenticated`) restores the session via `RestoreSession` in `build()`. Auto-retry is disabled, and the splash screen offers a manual retry instead.
- `login()` throws a `Failure` to the form rather than entering an error state.
- There is no logout endpoint: logout clears the stored tokens.
- `core/router/app_router.dart` bridges auth state into go_router's `refreshListenable`. The redirect sends no value to `/splash`, `Unauthenticated` to `/login`, and `Authenticated` away from login/splash.

**Features:** `auth` (sign-in, session, remembered email), `password_reset` (signed out, from "Forgot password?": `POST /auth/forgot-password` always succeeds, so never say an email has no account; `POST /auth/verify-pin` trades the 6-digit code (10 minutes, 5 tries, `auth.invalid_pin` shown under the code boxes) for a `ResetToken` kept in `PasswordResetDraft`; `POST /auth/reset-password` spends it within 15 minutes, and `auth.invalid_reset_token` offers "Send a new code", which returns to the code screen. One code a minute: "Send a new code" waits `PasswordPolicy.resendCooldown`. All three calls are `authenticated: false`, and the reset doesn't sign in: it ends on "Password updated" → sign-in), `settings` (Me → Settings at `/me/settings`: language and appearance as `ChoiceRow`s, then About with the installed version (`appVersionProvider`, via `package_info_plus`, which reads `version:` from pubspec.yaml as built for Android and iOS; tests use `FakeAppInfoRepository`, 1.4.0 build 27); EN/ES persisted in SharedPreferences, `null` follows the device; the compact `LanguageToggle` is only for the sign-in header), `clients` (the user's accounts), `contacts` (people at an account), `locations` (an account's sites), `team` (an account's members and their access), `access` (per-account permissions), `proposals` (an account's sales pipeline), `contracts` (an account's agreements), `invoices` (an account's bills and payments), `scopes` (the work agreed per area of a location), `calendar` (an account's visits by day), `jobs` (Today, an account's jobs, crew and checklist), `complaints` (an account's complaints, assigned and resolved), `tasks` (an account's to-dos), `profile` (Me: own profile via `PATCH /auth/me`, change password, Administration), `service_catalog` (`/service-catalog`), `notifications` (the user's inbox at `/me/notifications` and the unread count on Today's avatar), `shell`, `users` (user and role administration).

The detail (contract page layout): a head card (number, status, total, Edit pill, issue/due dates, then for issued ones a paid-of-total bar with the balance, red with days overdue, or "Paid in full"), Line items (`LineItemRow`, its `detail` naming the job), Payments (not on drafts; a voided one stays, muted and tagged; tapping a counted one voids it, confirmed: bounced check or refund) and the contract row. - **Scope of work** (`/accounts/:clientId/scopes`, a work-section module, `scope.view`): one list grouped by location (the server orders by location, then area), each row with the area (else the service, else "Whole site"), its first running time window and a frequency pill. `?contract=<id>` lists one contract's scopes; the contract detail's "Scopes of work" row opens it. - **Calendar** (`/accounts/:clientId/calendar`, a work-section module, `calendar.view`): a Monday-first `MonthGrid` (dot on days with events that aren't cancelled; the picked day filled, today outlined) and the picked day's events below. Create (dock's "+", `jobs.edit`) takes title, location (required; the only one is the default), an optional scope (fills location and an empty title) and when; an end before the start is on the next day, for night work. A new job opens its page, where crew and checklist are set. The job page (also under Today at `/today/job/:clientId/:jobId`; both stacks share `_jobRoutes`) offers, only while open (`Job.isOpen`: scheduled or in progress, else `jobs.closed`): Edit (`edit`, PATCH without crew or checklist), Crew (`crew`, `jobs.assign`: a `SwitchRow` per active non-client member from `membersProvider`, `PUT …/assignments`, sending back the role of who stays), Checklist (`checklist`: one field per item, new ones from the page action "+" → "Item"; `PUT …/checklist` replaces every item unticked, so it warns when some are ticked and sends nothing when unchanged) and Cancel; Delete only while scheduled (`canDelete`). Edit, Cancel and Delete sit in the header's "⋯" menu (`moreActions`). The page (modeled on `docs/job_detail.png`) is a summary card (status edge, time, duration and day with the status, kind, location and scope rows that open their pages from the account's stack, checklist progress with "Review tasks"), the field actions, an instructions card with Copy, and an activity log built from check-ins/outs, start, finish, score and sign-off (`_ActivityLog.eventsOf`). A calendar event that isn't cancelled or converted offers "Create job" (`jobs.edit`, `POST …/from-calendar-event`, its assignee as crew) and, once converted, an "Open job" row. Call `invalidateJobs(ref)` (Today, lists, job) after any write, plus `invalidateCalendar(ref)` after a conversion. While open, checklist rows tick off or reopen on tap (`POST …/checklist/:itemId/complete|reopen`, `TickChecklistItem`) for `jobs.edit` or the job's own crew (`Job.hasCrewMember`). **Field flow** (step 15), on the same page under the When card: check in → start → tick → complete → check out, the first one offered as the `PrimaryButton`, the rest `SecondaryButton`s (`_fieldActions`). Check in and out are only for the user on the crew (`Job.crewMember`; check out once checked in, also after completion); Start (scheduled) and Complete (in progress) for the crew or `jobs.edit`. Complete opens `complete` (`JobCompleteScreen`: optional 1–5 score as `ChoicePills`, crew notes, client sign-off name; notes unticked items without blocking; `POST …/complete` leaves empty fields out). The other actions take no body and act for the signed-in user. A crew member's own check-in shows as a success `Notice`.
- **Complaints** (`/accounts/:clientId/complaints`, a work-section module, `complaints.view`): a `PillToggle` between the ones being worked on, most urgent first (`openByUrgency`: priority, then newest), and the resolved ones (`resolvedLatestFirst`), each row with a status and priority pill (`ComplaintStatusLabel`, `PriorityLabel`). Report (dock's "+", `complaints.edit`) takes title and description (required), priority (`ChoicePills`, default medium), location, area, a job from the past 30 days (`accountJobsProvider`, `JobPeriod.past`; picking one fills an empty location) and, with `complaints.assign`, an assignee (active non-client members). Edit (`:id/edit`, PATCH, empty optional fields go as null) never sends the assignee: assigning is the detail's "Assigned to" row (`POST …/assign`, `complaints.assign`), and an assigned complaint is in progress. Resolve (`:id/resolve`, `ResolveComplaintScreen`, notes required) records who and when, and the detail then shows a Resolution card with `resolutionHours`. A resolved complaint is read-only until Reopen (a `LinkButton`, confirmed); reopening keeps the notes. Complaints are never deleted. **Photos** (at most `Complaint.maxPhotos`, 3; `photos` on every complaint row, URLs that may expire within the hour, so never cached): the report form picks them (`PhotoStrip`, a `FormSection`) and uploads them one by one after the create (`POST …/:id/photos`, multipart `photo`, 5 MB checked first by `AddComplaintPhoto`); a failed upload doesn't undo the complaint, a dialog says how many and why. After that they're added on the detail's Photos card and removed from the full-screen viewer (`showPhotoViewer`, `DELETE …/photos/:photoId`), with `complaints.edit` and only while not resolved (`complaints.already_resolved`). Edit doesn't touch photos. The picker (`core/media/photo_picker.dart`, `PickedPhoto` in `core/domain`) is shared with the profile photo, which passes `selfie: true` for the front camera. The detail follows the contract page's layout (head card with title, pills, reporter, Edit pill and description; a Details card of `FactRow`s that open the location and job). The job page ends with the job's complaints (`jobComplaintsProvider`, `GET …/complaints?jobId=`), shown with `complaints.view` when there are any or the user may report one; its "Report" (`complaints.edit`) opens `new?job=<id>`, which starts linked to the job and its location and goes back to the job on save. Like the job's location and scope rows, the rows and Report work only from the account's stack, not from Today. Call `invalidateComplaints(ref, clientId)` after any write (it also clears the per-job lists).
- **Tasks** (`/accounts/:clientId/tasks`, a work-section module, `tasks.view`): a `PillToggle` between open tasks (pending or in progress) and done ones (completed or cancelled), both in the server's order (soonest due first, undated last). Rows show who has it and the due day, with pills for status (none while pending), priority and how soon it's due (`taskDueLabel`: red once overdue from the API's `isOverdue`/`daysUntilDue`, orange today or tomorrow). Everything needs `tasks.edit`: create (dock's "+") and Edit (`:id/edit`, PATCH; empty optional fields go as null) take title (required), description, priority, a due day (`ymd`, "No due date" clears it) and an assignee (active non-client members, clearable; no separate assign endpoint). The detail (same layout as complaints) offers, while open, Complete (`POST …/complete`), Start for a pending one and Cancel (a `PATCH` with only `status`, confirmed); a done one is read-only until Reopen (back to pending). Delete (confirmed) removes it for good. Call `invalidateTasks(ref, clientId)` after any write.
- **Search on loaded lists:** the API can't search team, contacts, proposals, contracts, invoices, tasks or complaints, so their lists filter on the phone as you type with `matchesSearch` (`core/search/text_search.dart`: every word must appear, case and accents ignored), each through a `matches<Thing>` next to its screen listing the fields shown on the row plus status and priority names. The `SearchField` sits above the `PillToggle`, which then splits and counts only the matches; an empty result while searching shows "Nothing matches".
- **Notifications** (`/me/notifications`, a row at the top of Me with the unread count): the server writes them when work is assigned or changed (task or complaint assigned, complaint reported to the account's manager and supervisor, added to a job's crew, a job rescheduled or cancelled; never to whoever did it). Each carries a key (`NotificationTypes`) and `params`, never display text: `notificationHeadline` words it ("Carlos Medina assigned you a task", or a no-actor variant when `params.actorName` is null), and the row adds the item's title, a job's start, the account and when. Unknown keys still show (`notifOther`) but don't open. One page of the latest 100 (`GET /me/notifications?pageSize=100`), with a footnote when there are more. Tapping marks it read (`POST …/:id/read`, not awaited) and `context.go`es to the task, complaint or job in the Accounts stack (`notificationPath`), so its links work; "Mark all as read" is the header's ✓✓ (`POST …/read-all`). Call `invalidateNotifications(ref)` after either. **Push** (Firebase project `space-clean-llc-adc6c`, Android only so far; `lib/firebase_options.dart` and `android/app/google-services.json` come from `flutterfire configure`): `main` starts Firebase and sets `pushEnabledProvider` (off in tests and if Firebase fails, giving `DisabledPushRepository`). `PushListener` (around the router's pages in `App.builder`) registers the phone once signed in (`EnablePush`: the `spclean_default` channel, permission, `POST /me/devices {token, platform, language}`) and again when the token or app language changes, since the server words pushes in that language. Logout calls `DisablePush(true)` first (`DELETE /me/devices/:token`, 3 s at most), and any sign-out drops the token. Every push goes through `PushSource.of(data)`: ours (`source: 'spclean'`) refresh the count, are shown with `flutter_local_notifications` while the app is open (the OS only shows them when it's closed), and a tap marks the row read and opens `entityPath` like the inbox (a launch tap waits for the session). Stream Chat's (`sender: 'stream.chat'`) are ignored until chat exists and must go through the same listener. Push titles are written on the server (`src/notifications/push-message.ts`) with the same EN/ES text as the `notif*` ARB strings, so change both together. Tests use `FakePushRepository` (`pumpApp(push:)`).
- **Fresh data:** every provider that loads server data is a `FutureProvider.autoDispose` (`.autoDispose.family` for per-id data), so it loads again each time a screen opens it. Search and query notifiers stay plain. A picker that reads its list with `ref.read(x.future)` in a callback must also `ref.watch(x)` in `build` to keep it alive. After a write, still invalidate the lists that changed. When the app returns from the background, `RefreshOnReturn` (around the shell's body) reloads every mounted autoDispose `FutureProvider`, found by `LiveDataObserver` (`core/refresh/live_data.dart`, registered on the `ProviderScope` in `main.dart` and `pumpApp`). Nothing else has to be registered. A failed reload keeps the last value, so screens decide by `hasValue`, never by matching `AsyncData`: forms use `AsyncValue(value: final x?)`, or a failed reload would swap the form for an error and lose what was typed. Pushes refresh only the notification count; other screens don't get live updates (no sockets).
- **"+" inside an account:** option paths may contain `:clientId`, filled from the page. `_PlusOption.inAccount` gates an option by a permission on that account (`accountAccessProvider`); a plain `_PlusOption` gates by global role (Team's "Add to team").
- **Time:** `clockProvider` supplies "now" (tests pin it). Format dates and times with `core/l10n/formatting.dart`, which follows the locale and 12/24-hour setting.

**UI conventions**
- **Design system** (`lib/core/design/`, import `design.dart`), modeled on `docs/example_app.png` and the same on both platforms. Tokens: `SpaceColors` (`ground`, `surface`, `ink`, `accent`, `primary`, …), `SpaceRadius`, `SpaceSpace`. `SpaceColors` is a `ThemeExtension` with `light` and `dark` palettes, so always read colors with `context.colors.x`. Constants can't follow the theme, so give widgets nullable color parameters that resolve in `build`. `SpaceTheme.light()`/`dark()` set Manrope and orange pill `FilledButton`s. Appearance (System/Light/Dark, default System) lives in `settings` (`themeModeControllerProvider`, key `settings.theme_mode`), next to the language setting. Use `SpaceLogo` for the logo, which switches to the white knockout in dark mode. Every screen is a `SpacePage`: one header row with the back button (pushed screens), the title (or `heading:` for a `HeroHeadline`), and round `CircleButton`s with `PageBox`/`PageSliver` content. Components: `SpaceCard`, `StatCard`/`CardRow`, `TileCard`/`CardGrid`, `ListCard`/`ListRow`/`ChoiceRow`, `HeroHeadline` (two-tone), `SectionHeader`, `IconBadge`, `InitialsAvatar`, `StatusPill` (and, in `core/widgets`, `PriorityLabel` for the shared `Priority`), `SpaceProgressBar`, `AccentBanner`, `PrimaryButton`/`SecondaryButton`/`LinkButton` (optional `icon`, red with `destructive`)/`PillButton` (a card's corner "✎ Edit"), `CapsHeader`/`Fact`/`FactCard`/`FactRow` (detail pages' sections and label-over-value facts), `PillToggle`, `SwitchRow`/`SpaceSwitch`, `SpaceTextField`/`PickerField`/`ChoicePills`/`FormSection`, `SearchField`, `StatusIcon`, `Notice`, `SpaceBottomBar`, `AsyncSlivers`/`MessageSliver` (a first load shows a `shimmer` skeleton, `SkeletonSlivers`: pass `skeleton: SkeletonLayout.detail` or `.form` where the page isn't a list; no page-level spinners, only inside buttons and fields), `Shimmering`/`SkeletonBone`/`SkeletonListCard` (for loads outside `AsyncSlivers`), `RetryButton` (busy while the retry runs and for a moment after a tap, so a retry that fails again at once still visibly ran; `AsyncSlivers` and the splash use it). Don't use raw Material/Cupertino look-alikes or hard-coded colors.
- Only *behaviors* stay native (`core/widgets/adaptive.dart`, `core/design/widgets/pickers.dart`): adaptive dialogs (`adaptiveAction`), date, time and choice pickers, adaptive spinners, and page transitions. Visuals are the same on both OS. Pushed screens slide in from the right on both platforms, with the edge-swipe back (`SlidePageTransitions` in the theme's `pageTransitionsTheme`; Android's predictive back animation is not used). Every screen route is a `SlideRoute` (`core/router/transitions.dart`), which builds a `MaterialPage`; a plain `GoRoute` with `builder:` can end up with go_router's `NoTransitionPage` inside the tab navigators, so new routes should use `SlideRoute`. Top-level swaps (splash, login, the shell) cross-fade via `fadePage` (`core/router/transitions.dart`), and tab switches fade in via `FadeBranchContainer` (`features/shell/presentation/branch_container.dart`). All three are instant when the OS asks for reduced motion.
- **Phone numbers are US format.** Phone fields use `SpaceTextField(phone: true)`: "(713) 555-0142" mask, phone keypad, and a 10-digit check. Start the controller from `UsPhone.format(value)`, and show saved phones with `UsPhone.format` (`core/widgets/us_phone.dart`), which leaves numbers that aren't 10 digits as they were.
- All text renders at 90% of its design size (`SpaceTheme.textScale`, applied app-wide in `MaterialApp.builder`), on top of the OS text size. Set sizes at design size; don't compensate per widget.
- Use min-height rather than fixed heights for rows containing text, so 200% text scaling grows instead of clipping.
- `sharedPreferencesProvider` is loaded in `main()` and must be overridden. Tests use `test/helpers/test_app.dart` (`pumpApp`, fakes).

**Permissions:** global roles live in `User.roles` (`GlobalRole` constants). Per-client-account permissions come from `GET /clients/:id/members/me` → `permissions` (see section 5 of `docs/frontend-api.md`).

## Testing

`test/` mirrors `lib/`. Each layer is tested with a fake of the layer below it:
- **Use cases:** a fake `AuthRepository`.
- **Repository impls:** a fake remote data source plus `FlutterSecureStorage.setMockInitialValues({})`.
- **Network:** a fake Dio `HttpClientAdapter`.
- **Widget flows:** `pumpApp` in `test/helpers/test_app.dart` puts fakes behind every repository (auth, password reset, clients, contacts, locations, team, proposals, contracts, invoices, complaints, tasks, scopes, calendar, jobs, access, users, roles, profile, service catalog), pins the clock to `testNow`, and uses a phone-sized screen. `job()` builds test jobs.
- **Visual checks:** `tool/screenshots/threshold_screens_test.dart` renders sign-in (`threshold_*`) and signed-in (`app_*`, with synthetic demo data) sheets in real fonts (Roboto stands in for San Francisco), and asserts each frame shows the state it claims.
