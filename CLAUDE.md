# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

`sp_cln_app` is a Flutter **mobile** app (Android and iOS only; Dart SDK `^3.13.4`) for a REST backend documented in `docs/frontend-api.md` (endpoints, envelope, permission model) and `docs/api-message-keys.md` (every translation key the API can return). `docs/` is git-ignored, so read those files locally before building a feature against an endpoint. The backend source (NestJS + Prisma) is at `D:\DevProjects\sp_cln_be`. Its DTOs (`src/**/dto/*.ts`) are the exact request contract (unknown fields are rejected), and they cover details the docs leave out, such as which fields `PATCH` accepts.

Stack: Riverpod 3 (no codegen), Dio, go_router, flutter_secure_storage, shared_preferences, flutter_svg, gen-l10n (English + Spanish).

Product and design context: `PRODUCT.md` (users, roles, principles, accessibility) and `DESIGN.md` (visual system). Read them before UI work.

On a Windows dev machine, building with plugins requires Developer Mode (symlink support).

The app is mobile only. Don't add web or desktop code paths (`kIsWeb`, desktop-only plugins). The backend also doesn't send CORS headers, so a web build couldn't reach it.

## Architecture: Clean Architecture, feature-first

```
lib/core/                 cross-cutting: error/ (Failure), usecase/, network/, storage/, di/, router/, l10n/, theme/, widgets/
lib/features/<feature>/
  domain/                 entities/, repositories/ (abstract interfaces), usecases/  — pure Dart
  data/                   models/ (JSON → entity), datasources/, repositories/ (*_impl)
  presentation/           controllers/ (Riverpod notifiers), screens/
  di/                     <feature>_providers.dart — composition root
```

**Dependency rule, which must hold:**
- `domain/` imports only other domain code, `core/error` and `core/usecase`: no Flutter, Dio, Riverpod or `data/`.
- `presentation/` never imports `data/` or `core/network`. Controllers call use cases, and screens catch `Failure`.
- Only `di/` files know the concrete `*Impl` classes.

**Adding a feature** follows the auth layout:
1. Entity plus an abstract repository in `domain/`, with one use case class per action (`UseCase<T, Params>`, called via `call`).
2. A remote data source that calls `ApiClient` and throws `ApiException`. A model that maps JSON to the entity.
3. A `*RepositoryImpl` that wraps every call so each `ApiException` becomes a `Failure` via `toFailure()` (see `_guard` in `AuthRepositoryImpl`).
4. Providers in `di/`, then controllers and screens.

**Errors:** every error surfaced to the UI is a domain `Failure` (`core/error/failures.dart`): `NetworkFailure`, `UnauthorizedFailure` (401), `ValidationFailure` (field errors keyed by request-body path) or `ServerFailure`. `messageKey` is the API's translation key, never display text. `lib/core/l10n/failure_messages.dart` turns keys into localized strings (`failureMessage`, `fieldError`). Add a case there whenever a feature starts surfacing a new key.

**API layer (`core/network/`)**
- `ApiClient` unwraps the `{ success, message, data, errors, statusCode }` envelope.
- `AuthInterceptor` attaches the bearer token. On 401 with `auth.invalid_access_token`/`auth.missing_token`, it refreshes once through a separate interceptor-less Dio, with concurrent 401s sharing one refresh, and then replays the request. Any refused refresh (a 4xx other than 408/429), or a replay still refused with fresh tokens, calls `TokenStorage.expireSession()`, which emits on `sessionExpired`; `AuthController` listens through the `WatchSessionExpired` use case and the router goes to sign-in. Offline, a timeout, 408/429 or 5xx during refresh keep the session, and the request fails with that error instead of the 401 (which would read "session expired"). `test/features/auth/presentation/session_expiry_test.dart` runs the real chain with only the HTTP adapter faked.
- Public calls pass `authenticated: false`.
- The backend rejects unknown body fields (`validation.whitelist_validation`), so send only the fields an endpoint defines.

**Session and routing**
- `authControllerProvider` (`AsyncNotifier<AuthState>`, sealed `Authenticated(user)` / `Unauthenticated`) restores the session via `RestoreSession` in `build()`. Auto-retry is disabled, and the splash screen offers a manual retry instead.
- `login()` throws a `Failure` to the form rather than entering an error state.
- There is no logout endpoint: logout clears the stored tokens.
- `core/router/app_router.dart` bridges auth state into go_router's `refreshListenable`. The redirect sends no value to `/splash`, `Unauthenticated` to `/login`, and `Authenticated` away from login/splash.

**Features:** `auth` (sign-in, session, remembered email), `password_reset` (email → 6-digit code → new password; its repository throws `UnavailableFailure` until the backend defines reset endpoints, so don't guess that contract), `settings` (Me → Settings at `/me/settings`: language and appearance as `ChoiceRow`s; EN/ES persisted in SharedPreferences, `null` follows the device; the compact `LanguageToggle` is only for the sign-in header), `clients` (the user's accounts), `contacts` (people at an account), `locations` (an account's sites), `team` (an account's members and their access), `access` (per-account permissions), `proposals` (an account's sales pipeline), `contracts` (an account's agreements), `scopes` (the work agreed per area of a location), `calendar` (an account's visits by day), `jobs` (Today, an account's jobs, crew and checklist), `profile` (Me: own profile via `PATCH /auth/me`, change password, Administration), `service_catalog` (`/service-catalog`), `notifications` (unread count for Today's avatar; a placeholder until the API has it), `shell`, `users` (user and role administration).

**Signed-in app:** `StatefulShellRoute` with three branches (`/today`, `/accounts`, `/me`), each with its own stack (`features/shell/presentation/app_shell.dart`, custom `SpaceBottomBar`: a floating dock of icon-only tabs). The dock has only Today and Accounts: Me has no tab and opens from the avatar on Today (tooltip "Me", so tests use `find.byTooltip('Me')` from Today), and its root's back button and the system back return to Today (`SpacePage.onBack`). The avatar carries a `CountBadge` of unread notifications (`unreadNotificationsProvider`); until the backend defines notification endpoints, the `notifications` repository returns a placeholder 3 (`NotificationsRepositoryImpl.placeholderUnread`; don't guess that contract), and `pumpApp` defaults to 0 unread. The "+" beside the dock is the app's only "+" (screens have none). Its options follow the page on top: `_byPage` in `app_shell.dart` maps a route pattern to options, `_noPlus` hides it on forms, and other pages get `_everywhere`. Each option is gated by a global-role policy. When a list page gets a create form, add its route there instead of a header button. A page that adds inside its own state (the proposal form's line items) takes "+" with `PageActionHost.registerPageAction` (`features/shell/presentation/page_action.dart`); it shows only while that page is on top, even on forms. Pass `text` ("Line item") so the "+" widens into a pill naming what it adds (plain "+" again at 150% text and up). Riverpod auto-retry is off (`retry: (_, _) => null` in `main.dart` and tests).
- **No cross-account endpoints:** jobs, calendar, complaints and tasks live under `/clients/:clientId/...`. Today merges accounts in `GetDayJobs` (one request per account in parallel; 403 accounts are skipped, other failures reported as `failedClients`).
- **Permissions:** build every action from `accountAccessProvider(clientId).can(Permissions.x)`, never from the role name. Global owners bypass membership (no request). Everyone else reads `GET /clients/:id/members/me`, which every member may call; a 403 means not a member (`AccountAccess.none`). `GET /clients` is already filtered to the user's accounts.
- **Own profile:** Me → Edit (`/me/edit`) is open to everyone and sends only `name`, `phoneNumber` and the emergency contact (`PATCH /auth/me`); the saved user goes back into `AuthController.replaceUser`. Email, roles and pay stay with owners in user administration. Change password is `/me/password`. The profile photo is changed from the avatar on Me (`ProfilePhotoButton`: take, choose or remove) via `PUT`/`DELETE /auth/me/photo` (multipart field `photo`, 5 MB checked first by `SetMyPhoto`); `photoPickerProvider` wraps `image_picker` (downscaled to 1600 px JPEG) and tests use `FakePhotoPicker`. Only users can change their own photo. Anywhere a `photoUrl` is known, pass it to `InitialsAvatar(photoUrl:)`, which shows initials while the photo loads or if it fails. `AuthInterceptor` clones a `FormData` body before replaying it after a refresh.
- **Service catalog** (`/me/services`, Administration): owners and account managers (`ServiceCatalogPolicy.canManage`) maintain it. Three list pages share `_CatalogPage` (a search-only `CatalogQuery` per `CatalogList`; no status filter, every row has a `StatusIcon` and inactive titles are muted, like the users list): every service at `/me/services` in one list by name, and `/me/services/categories` and `/me/services/units`, reached from the dock's "+". Services pick a category (optional) and a unit (required) from the active ones and show prices as `$0.12` with "Janitorial · per sq ft" (`UnitOfMeasure.short`). Services are never deleted, only set inactive. Categories and units share `LookupFormScreen`: Delete shows only while `serviceCount` is 0, otherwise the form says to set it Inactive. After any save or delete call `invalidateCatalog(ref)`. Later pickers should query `isActive: true`.
- **User administration** lives under Me → Administration (`/me/users`, `/me/roles`). It's visible to global `owner` and `account_manager` (`UserAdminPolicy.canView`), and only owners get write controls (`canEdit`). The Administration rows come from `adminModules` in `features/profile/presentation/admin_modules.dart`. Each entry has its own global-role visibility rule, so a new tool is one route under `/me` plus one entry there. Users are never deleted, only deactivated with `PATCH {isActive}`. Roles change via `PUT /users/:id/roles`, which `UpdateUser` calls only when they changed. Owners can reset a password by setting a new one in Edit. Forms are `FormSection`s (titled white cards) of `SpaceTextField`/`PickerField`, with roles as `ChoicePills` and a `PrimaryButton` pinned at the bottom. Server field errors are shown by re-running the validators after a failed save.
- **Account screen modules:** the account screen shows what a member can open as one `ListCard` of `ListRow`s (icon, name, what's inside), with no section headings. The rows come from `accountModules` in `features/clients/presentation/account_modules.dart`, filtered by permission (`orderedModules`). Only built modules get an entry, and there are no "coming soon" placeholders. The header's Reorder button turns the rows into drag handles; the order is the user's, the same in every account, saved on the device (`moduleOrderProvider`, key `accounts.module_order`). Modules hidden in one account keep their place (`reorderVisible`). Until the user reorders, `AccountSection` sets the default (work first, then the account's records), and a new module joins the end of a saved order. To add a module, give it a route under `/accounts/:clientId` and an entry there.
- **Account management** (`clients`): the Accounts tab's "+" (`/accounts/new`) is shown to global `owner`/`account_manager` (`AccountAdminPolicy.canCreate`). The Account details tile opens `/accounts/:id/info` (`info.view`). The page (modeled on `docs/new_account_details.png`) is an overview card (avatar, names, status, an Edit pill, then a two-column fact grid that turns to one column at 150% text) and "People in charge" rows (name over role); the header has no actions. Edit (`info/edit`, the overview's Edit pill) needs `info.edit`, and Delete (the red link at the bottom) is for owners only. The API refuses to delete an account with history (`clients.has_related_records`); that refusal opens the purge page instead (`info/purge`, `PurgeAccountScreen`, `DELETE /clients/:id/purge`), which suggests Inactive and enables its button only once the legal name is typed (`AccountAdminPolicy.confirmsPurge`). The client can't tell beforehand whether an account has history, so the plain delete always runs first. Creating an account doesn't make its creator a member, so only owners are taken to it afterwards. Everyone else gets a notice. Assignee pickers need `GET /users`, and they stay read-only for anyone who can't list users. On edit, assignees and status are sent only when they changed.
- **Contacts** (`/accounts/:clientId/contacts`, an Account-section module): listing needs `info.view`; add (from the dock's "+"), edit and delete need `info.edit`. The list isn't paginated and comes primary first; the detail screen reads from it (`contactProvider`), so invalidate `contactsProvider(clientId)` after any write. Setting Primary or Billing takes it from the other contacts on the server. Only global owners give a login (`ContactLoginPolicy`, `…/:contactId/login`), and only to a contact with an email. Deleting a contact leaves their login and membership, and the confirmation says so.
- **Locations** (`/accounts/:clientId/locations`, an Account-section module): same permissions as contacts. The list is searched on the server (name, address, city) per account (`locationSearchProvider`), and the detail reads `GET …/locations/:id` for the scope and job counts. Create/update responses carry no counts, so call `invalidateLocations(ref, clientId)` after any write. Square footage and floors are sent as numbers. There's no inactive state: Delete shows only while nothing uses the location, otherwise the screen says why.
- **Team & access** (`/accounts/:clientId/team`, an Account-section module, `team.view` to see it): every change is for global owners only (`TeamPolicy.canManage`); the API checks the role, not `team.manage`. Adding picks an active user who isn't a member yet and suggests the base role from their global roles. Access is edited as View/Edit/Assign… switches per area (`AccessList`, `SwitchRow`; read-only it shows check/dash marks); turning an action on turns on that area's View, and turning View off clears the area (`PermissionCatalog.toggled`). The catalog and each role's defaults come from `GET /permissions`. `UpdateMemberAccess` posts the base role only when it changed, then PUTs the overrides worked out against the new role's defaults (the API keeps old overrides across a role change, and PUT replaces them all). Later assignee pickers read `membersProvider(clientId)`.
- **Proposals** (`/accounts/:clientId/proposals`, a work-section module, `proposal.view`): one list of negotiations (each its current version), newest first, each row with a stage pill (`ListRow.tag`) and the price. The API can't search proposals, so the search runs on the loaded list (`matchesProposal`: line items, note, stage name, preparer; case and accents ignored). Create (dock's "+"), Edit (`:id/edit`, PATCH), New version (`:id/version`) and Approve (`:id/approve`) need `proposal.edit`, and only while the version is current and not approved (`Proposal.isOpen`); older versions open read-only from the detail's Versions list. Delete (the detail header's trash button, same rule) removes the whole negotiation, every version, via `DELETE …/proposals/:id`; the API refuses it once any version is approved (`proposals.already_approved`) or a contract uses one (`proposals.has_related_records`). Approved is reached only by approving, so the stage picker offers `ProposalStage.open`. The form is one headingless card: stage and note, the line item rows between hairlines, then the agreed price, valid-until and total; new items come from the dock's "+" (a page action), and a row swiped right-to-left is removed (`_SwipeToRemove`, also a screen-reader action), and each item is added or edited on its own page (`LineItemScreen`, an `item` child route of each form, item passed in `extra` and handed back on pop as a `LineItemResult`). Picking a service there (`activeServicesProvider`) fills the description and price unless typed by hand. Rows with a trailing figure (`LineItemRow`, `ProposalRow`) move it under the title at 150% text and up (`isLargeText`). Money stays as decimal strings; sum with `toCents`, never send `lineTotal`. A create or new version goes to its own page (new id); call `invalidateProposals(ref, clientId)` after any write.
- **Contracts** (`/accounts/:clientId/contracts`, a work-section module, `contract.view`): one list, latest start first, each row with its term, a status pill (`ContractStatusLabel`; an active contract within 30 days shows "Expiring soon" from the API's `isExpiringSoon`, which isn't a status) and the value. A `PillToggle` narrows the loaded list to the expiring ones. Create (dock's "+", or "Create contract" on an approved proposal, which opens `new?proposal=<id>`), Edit (`:id/edit`), Sign (`:id/sign`, a day up to today; today is sent as no date) and Cancel need `contract.edit` and only while not cancelled (`Contract.isEditable`); signing happens once (`canSign`) and activates it. The server never expires a contract, so every active one offers Mark expired (`canMarkExpired`, a `PATCH` with only `status`), and one past its end date shows "Ended …" in red; an expired contract can still be edited or cancelled. Delete is only for a draft with no scopes or invoices (`canDelete`). The detail page (modeled on `docs/new_contract.png`) has no header actions: a value card (status, "Contract value", an Edit pill, the date range with "Term: …" from `Contract.term`, time left), then capitals-titled cards for schedule & terms (label-over-value facts, two to a row) and execution & documents (signature, scopes, proposal), with Sign as a `PrimaryButton` and Mark expired, Cancel and Delete as `LinkButton`s at the foot. A new contract's proposal is picked from the approved ones (needs `proposal.view`) and fills the value; it's fixed afterwards, so PATCH never sends `proposalId`. The value is always sent (the column is required), and on edit empty optional fields go as null to clear them. Call `invalidateContracts(ref, clientId)` after any write.
- **Scope of work** (`/accounts/:clientId/scopes`, a work-section module, `scope.view`): one list grouped by location (the server orders by location, then area), each row with the area (else the service, else "Whole site"), its first running time window and a frequency pill. `?contract=<id>` lists one contract's scopes; the contract detail's "Scopes of work" row opens it. Create (dock's "+") and Edit (`:id/edit`) need `scope.edit`; a new scope picks a contract that isn't cancelled and keeps it (PATCH never sends `contractId`), and a single contract or location is taken as the default. Delete (header trash) only while `jobCount` is 0; otherwise the page says to pause its windows. Time windows (`ScopeSchedule`, times as `ClockTime` "HH:MM") are added with the form's page action ("+" → "Time window") and edited on their own page (`TimeWindowScreen`, a `window` child route, `TimeWindowArgs` in `extra`, `TimeWindowResult` handed back): weekdays as `ChoicePills` only for weekly/biweekly (`ScopeFrequency.needsDays`), start/end via `showAppTimePicker`, and a Running switch. Sending `schedules` replaces every window and unlinks the jobs and calendar events made from the old ones, so an edit sends them only when the windows or the frequency changed (`ScopeDraft.schedules` null keeps them). Call `invalidateScopes(ref)` and `invalidateContracts(ref, clientId)` after any write.
- **Calendar** (`/accounts/:clientId/calendar`, a work-section module, `calendar.view`): a Monday-first `MonthGrid` (dot on days with events that aren't cancelled; the picked day filled, today outlined) and the picked day's events below. The picked day lives in `calendarDayProvider(clientId)` (plain, null = today) so the dock's "+" (`calendar.edit`) starts a one-off event on it. Each month is one `MonthQuery`; for `calendar.edit` users `GetMonthEvents` first runs `POST …/generate` for the month (idempotent; a failed fill still lists), so the screen waits for `accountAccessProvider` before loading. Any event can be deleted until it's a job (`canDelete`); the backend remembers a deleted generated event's slot, so filling the month again doesn't bring it back (the confirmation says so). Edit (`:id/edit`) never sends the date or start: moving is Reschedule (`:id/reschedule`, `POST …/reschedule` with the end always sent, null to clear), which keeps a history shown under "Moves". Cancelled events and those turned into jobs (`isEditable`) are read-only. The form's location, scope and assignee pickers read `allLocationsProvider` (`info.view`), `scopesProvider` (`scope.view`) and `membersProvider` (`team.view`) and say why when a list can't load. A moved generated event keeps its original slot on the server, so generating doesn't recreate it. Call `invalidateCalendar(ref)` after any write.
- **Jobs, office side** (`/accounts/:clientId/jobs`, a work-section module, `jobs.view`): a `PillToggle` between Upcoming (from today on) and the past 30 days, each with its count (`JobQuery`, `GetAccountJobs`; both load), then the picked day's heading, a strip of days (dot = has jobs; defaults to the first upcoming or latest past day with work; "Today" jumps back), and that day's `JobCard`s; the header's filter button narrows by status on the phone (`CircleButton.light(active:)`). Create (dock's "+", `jobs.edit`) takes title, location (required; the only one is the default), an optional scope (fills location and an empty title) and when; an end before the start is on the next day, for night work. A new job opens its page, where crew and checklist are set. The job page (also under Today at `/today/job/:clientId/:jobId`; both stacks share `_jobRoutes`) offers, only while open (`Job.isOpen`: scheduled or in progress, else `jobs.closed`): Edit (`edit`, PATCH without crew or checklist), Crew (`crew`, `jobs.assign`: a `SwitchRow` per active non-client member from `membersProvider`, `PUT …/assignments`, sending back the role of who stays), Checklist (`checklist`: one field per item, new ones from the page action "+" → "Item"; `PUT …/checklist` replaces every item unticked, so it warns when some are ticked and sends nothing when unchanged) and Cancel; Delete only while scheduled (`canDelete`). Edit, Cancel and Delete sit in the header's "⋯" menu (`moreActions`). The page (modeled on `docs/job_detail.png`) is a summary card (status edge, time, duration and day with the status, kind, location and scope rows that open their pages from the account's stack, checklist progress with "Review tasks"), the field actions, an instructions card with Copy, and an activity log built from check-ins/outs, start, finish, score and sign-off (`_ActivityLog.eventsOf`). A calendar event that isn't cancelled or converted offers "Create job" (`jobs.edit`, `POST …/from-calendar-event`, its assignee as crew) and, once converted, an "Open job" row. Call `invalidateJobs(ref)` (Today, lists, job) after any write, plus `invalidateCalendar(ref)` after a conversion. While open, checklist rows tick off or reopen on tap (`POST …/checklist/:itemId/complete|reopen`, `TickChecklistItem`) for `jobs.edit` or the job's own crew (`Job.hasCrewMember`). **Field flow** (step 15), on the same page under the When card: check in → start → tick → complete → check out, the first one offered as the `PrimaryButton`, the rest `SecondaryButton`s (`_fieldActions`). Check in and out are only for the user on the crew (`Job.crewMember`; check out once checked in, also after completion); Start (scheduled) and Complete (in progress) for the crew or `jobs.edit`. Complete opens `complete` (`JobCompleteScreen`: optional 1–5 score as `ChoicePills`, crew notes, client sign-off name; notes unticked items without blocking; `POST …/complete` leaves empty fields out). The other actions take no body and act for the signed-in user. A crew member's own check-in shows as a success `Notice`.
- **Fresh data:** every provider that loads server data is a `FutureProvider.autoDispose` (`.autoDispose.family` for per-id data), so it loads again each time a screen opens it. Search and query notifiers stay plain. A picker that reads its list with `ref.read(x.future)` in a callback must also `ref.watch(x)` in `build` to keep it alive. After a write, still invalidate the lists that changed. When the app returns from the background, `RefreshOnReturn` (around the shell's body) reloads every mounted autoDispose `FutureProvider`, found by `LiveDataObserver` (`core/refresh/live_data.dart`, registered on the `ProviderScope` in `main.dart` and `pumpApp`). Nothing else has to be registered. A failed reload keeps the last value, so screens decide by `hasValue`, never by matching `AsyncData`: forms use `AsyncValue(value: final x?)`, or a failed reload would swap the form for an error and lose what was typed. There's no push from the server yet (no sockets).
- **"+" inside an account:** option paths may contain `:clientId`, filled from the page. `_PlusOption.inAccount` gates an option by a permission on that account (`accountAccessProvider`); a plain `_PlusOption` gates by global role (Team's "Add to team").
- **Time:** `clockProvider` supplies "now" (tests pin it). Format dates and times with `core/l10n/formatting.dart`, which follows the locale and 12/24-hour setting.

**UI conventions**
- **Design system** (`lib/core/design/`, import `design.dart`), modeled on `docs/example_app.png` and the same on both platforms. Tokens: `SpaceColors` (`ground`, `surface`, `ink`, `accent`, `primary`, …), `SpaceRadius`, `SpaceSpace`. `SpaceColors` is a `ThemeExtension` with `light` and `dark` palettes, so always read colors with `context.colors.x`. Constants can't follow the theme, so give widgets nullable color parameters that resolve in `build`. `SpaceTheme.light()`/`dark()` set Manrope and orange pill `FilledButton`s. Appearance (System/Light/Dark, default System) lives in `settings` (`themeModeControllerProvider`, key `settings.theme_mode`), next to the language setting. Use `SpaceLogo` for the logo, which switches to the white knockout in dark mode. Every screen is a `SpacePage`: one header row with the back button (pushed screens), the title (or `heading:` for a `HeroHeadline`), and round `CircleButton`s with `PageBox`/`PageSliver` content. Components: `SpaceCard`, `StatCard`/`CardRow`, `TileCard`/`CardGrid`, `ListCard`/`ListRow`/`ChoiceRow`, `HeroHeadline` (two-tone), `SectionHeader`, `IconBadge`, `InitialsAvatar`, `StatusPill`, `SpaceProgressBar`, `AccentBanner`, `PrimaryButton`/`SecondaryButton`/`LinkButton` (optional `icon`, red with `destructive`)/`PillButton` (a card's corner "✎ Edit"), `PillToggle`, `SwitchRow`/`SpaceSwitch`, `SpaceTextField`/`PickerField`/`ChoicePills`/`FormSection`, `SearchField`, `StatusIcon`, `Notice`, `SpaceBottomBar`, `AsyncSlivers`/`MessageSliver`, `RetryButton` (busy while the retry runs and for a moment after a tap, so a retry that fails again at once still visibly ran; `AsyncSlivers` and the splash use it). Don't use raw Material/Cupertino look-alikes or hard-coded colors.
- Only *behaviors* stay native (`core/widgets/adaptive.dart`, `core/design/widgets/pickers.dart`): adaptive dialogs (`adaptiveAction`), date, time and choice pickers, adaptive spinners, and page transitions. Visuals are the same on both OS. Pushed screens slide in from the right on both platforms, with the edge-swipe back (`SlidePageTransitions` in the theme's `pageTransitionsTheme`; Android's predictive back animation is not used). Every screen route is a `SlideRoute` (`core/router/transitions.dart`), which builds a `MaterialPage`; a plain `GoRoute` with `builder:` can end up with go_router's `NoTransitionPage` inside the tab navigators, so new routes should use `SlideRoute`. Top-level swaps (splash, login, the shell) cross-fade via `fadePage` (`core/router/transitions.dart`), and tab switches fade in via `FadeBranchContainer` (`features/shell/presentation/branch_container.dart`). All three are instant when the OS asks for reduced motion.
- **Phone numbers are US format.** Phone fields use `SpaceTextField(phone: true)`: "(713) 555-0142" mask, phone keypad, and a 10-digit check. Start the controller from `UsPhone.format(value)`, and show saved phones with `UsPhone.format` (`core/widgets/us_phone.dart`), which leaves numbers that aren't 10 digits as they were.
- All text renders at 90% of its design size (`SpaceTheme.textScale`, applied app-wide in `MaterialApp.builder`), on top of the OS text size. Set sizes at design size; don't compensate per widget.
- Use min-height rather than fixed heights for rows containing text, so 200% text scaling grows instead of clipping.
- `sharedPreferencesProvider` is loaded in `main()` and must be overridden. Tests use `test/helpers/test_app.dart` (`pumpApp`, fakes).

**Permissions:** global roles live in `User.roles` (`GlobalRole` constants). Per-client-account permissions come from `GET /clients/:id/members/me` → `permissions` (see section 5 of `docs/frontend-api.md`).

## Testing

`test/` mirrors `lib/`. Each layer is tested with a fake of the layer below it:
- **Use cases:** a fake `AuthRepository`.
- **Repository impls:** a fake remote data source plus `FlutterSecureStorage.setMockInitialValues({})`.
- **Network:** a fake Dio `HttpClientAdapter`.
- **Widget flows:** `pumpApp` in `test/helpers/test_app.dart` puts fakes behind every repository (auth, password reset, clients, contacts, locations, team, proposals, contracts, scopes, calendar, jobs, access, users, roles, profile, service catalog), pins the clock to `testNow`, and uses a phone-sized screen. `job()` builds test jobs.
- **Visual checks:** `tool/screenshots/threshold_screens_test.dart` renders sign-in (`threshold_*`) and signed-in (`app_*`, with synthetic demo data) sheets in real fonts (Roboto stands in for San Francisco), and asserts each frame shows the state it claims.
